# Attachment Cloud Cache（附件云端缓存）

[English](./README.md) · **简体中文**

把笔记里的附件上传到**你自己的** S3 兼容存储，同时在缓存目录里留一份本地副本 —— 于是断网时图片照样能显示。

> **状态：早期开发（0.1.0）。** 项目按 TDD 逐个功能推进。下面「今天能用的」与「已验证的范围」是**权威清单**：
> 哪些做完了、哪些是刻意还没做的，以那两节为准。
>
> **今天能用的：** 设置页（存储连接设置，含「测试连接」按钮）；**上传** —— 粘贴或拖入图片会把它上传、保留一份
> 本地副本，并把笔记里的链接改写成指向你的存储；**离线渲染** —— 来自你存储的图片在阅读视图与实时预览里都会被
> 换成本地副本，站外图片一律不碰；**按需补回缺失的副本**（换了设备，或你清过缓存）；**缓存站外图片** —— 默认关闭；
> 打开后，同一站点的图片只问**一次**，你同意才会下载、上传到你的存储并改写笔记里的链接（你拒绝过的站点不会再问）；
> **缓存容量上限** —— 默认关闭；设了上限就在后台按最近最少使用删掉，磁盘空间立刻释放（再看时它们会回来）；
> 以及四条维护命令（查看缓存占用、自检并修复索引、清理未使用的缓存文件、上传已存在的附件）。
> 桌面端与移动端都要求 Obsidian 1.13.0+。
>
> **还没被证明的：** 「测试连接」已在真实 MinIO 实例上跑通，但**上传与下载还没有**；而且
> **iOS 与 Android 从未运行过** —— 这留下了哪些没被证明的东西，见下面「已验证的范围」。桌面端是另一回事：
> 它**真的**被驱动过，连 Obsidian 一起（`npm run verify:real`）。

## 为什么还要再做一个附件插件

这个问题的两半通常由两个不同的插件分别解决，而各自留下的缺口是**结构性的**，不是少个功能：

- **上传类插件**把笔记改成指向远端地址 —— 通常还会删掉本地文件、或不再引用它。这样便于发布与同步，
  但**断网时图片就断了**。
- **「本地化」类插件**把远端图片下载回 vault —— 于是你必须**先联网至少一次**，离线才可能生效。

本插件两件都做，且顺序固定：先上传，然后把本地文件**留作缓存**而不是丢掉。笔记仍然指向你的存储
（可迁移、可分享、vault 小），而渲染用本地副本（没有网络也能显示；离线时**零**远端请求 —— 副本本来就在）。

这两半是**设计上耦合**的，不是为了顺手打包在一起：如果别的插件先上传了那个文件，它早就把本地副本处理掉了，
也就没什么可缓存的了。

## 功能

- **S3 兼容存储**：Cloudflare R2、AWS S3、MinIO、Backblaze B2，以及任何 S3 兼容端点
- **默认按内容寻址**（`{hash}.{ext}`），同一张图只存一份
- **粘贴与拖拽时立刻上传**
- **从本地缓存离线渲染** —— 缓存镜像你的桶结构，且可随时整体删除（会按需重建）
- **不会丢图**：上传失败时，文件会被写进你的附件目录并插入一条可用的本地链接，同时说明原因
- **桌面端与移动端**
- **秘密密钥留在钥匙串** —— `data.json` 里只写访问密钥 **ID**，那是标识符、不是秘密（见「披露」）

### 几个值得知道的实现选择

- **不依赖 AWS SDK。** SigV4 签名是自己写的（约 160 行代码），并用 AWS 官方公布的测试向量校验过 ——
  所以插件没有重依赖、也没有打包进来的 SDK。签名出错这类 bug 极贵，所以签名器由 **AWS 自己公布**的向量钉住：
  任何一个字节错了，签名就对不上。
- **只在重试有帮助时才重试。** 是否重试是一份白名单：网络失败与 5xx/429/408，配上限定的指数退避。
  4xx 永不重试 —— 被拒的请求重发还是会被拒，而对凭据错误重试只会把「去改设置」变成「卡几秒，然后同样失败」。
- **错误信息里永远不含你的秘密密钥。** 外发文案**无条件脱敏**，而不是指望服务端什么都不回显。
- **不用 Node 内置模块。** 只使用两端都有的 API，因为移动端根本没有那些模块。这一条由 lint 保证，不是靠自觉。

### 粘贴或拖入一张图时发生了什么

1. 字节**先**写进你的附件目录，然后才尝试上传。顺序很重要：插件已经把 Obsidian 自己对这次粘贴的处理取消了，
   所以从那一刻起，图片能否留下只取决于插件有没有把它落盘。先写意味着最坏情况是「图还在，只是没上传」，
   而不是图没了。
2. 上传，成功后把本地文件**移动**进缓存目录（不是复制，也绝不删除）。
3. 上传失败时你会得到一条可用的本地嵌入链接，外加一条说明原因的提示 —— 笔记照样能用，也没有东西被悄悄丢掉。

有两条护栏是有意为之，值得知道：

- **同一张图粘两次不发任何网络请求。** key 由内容哈希推导，对象本来就在那儿。
- **同名文件绝不覆盖。** 名字会被做成唯一的（`a.png` → `a 1.png`），判定时同时查 Obsidian 的索引与真实磁盘 ——
  因为两者互相滞后。

拿不准你的意图时，插件会让开。带文字的粘贴交给 Obsidian（你多半在粘文字），vault 内部的拖拽也交给 Obsidian
（你多半在移动笔记）。如果一次粘贴里含有插件不处理的文件类型，**整批**原样放行而不是处理其中一部分 ——
处理一部分意味着其余部分被丢掉、且没有东西能放回去。

## 已验证的范围（信它之前先读这节）

把「真的被验证过什么」说准，比列一长串功能重要：

| 范围 | 怎么验证的 |
|---|---|
| 签名、key/路径推导、设置合并、缓存索引、文件命名 | 穷举式单元测试，外加变异验证：每条规则都必须因**它自己的原因**变红 |
| SigV4 的正确性 | 三条 AWS 公布的向量（含一个带查询排序与 `$` 编码的 S3 示例） |
| 上传/下载/HEAD/DELETE 与重试策略 | 一个**真实本地 HTTP 服务**，它**独立重算**签名 —— 不是用插件自己的代码 |
| 上传链路：字节一致、恰好 1 次 PUT 与 0 次 GET、本地文件是移动而非复制、上传失败仍保留字节、同名文件不被覆盖 | 同一个真实 HTTP 服务 + 真实文件系统 |
| 粘贴/拖拽的判定 | 对判定本身做穷举边界测试 —— 判错一个就可能吞掉你的内容 |
| 粘贴/拖拽的执行 | 一个会记录的编辑器替身，断言插入了什么文本、插在哪里、以及没有东西丢失 |
| 插件**真的接上线了** | 加载**真实构建产物** `main.js`、跑 `onload()`，全链路驱动：一次粘贴（恰好 1 次 PUT、缓存副本字节一致、链接被插入、再粘一次相同内容 0 次 PUT）、**阅读视图与实时预览两种**渲染（`src` 被换成本地副本、**零**请求、站外图不动）、`clean-cache`（孤儿文件经 `Vault.delete` 删除且绝不碰系统回收站、确认文案如实说明、仍被引用的副本保留、**取消则什么都不动**）、批量上传（两种链接形态都被改写、原件保留）。把 `src/main.ts` 里任何一行注册删掉，这个测试就会失败 —— 这就是它的意义 |
| 哈希 | 在 padding 边界与密钥长度边界上，逐字节与 `node:crypto` 比对 |

**已部分在真实服务商上验证：**「测试连接」—— 一次对桶的签名 `HEAD` —— 已在一个真实 MinIO 实例上通过，
也就是说端点、凭据、SigV4 签名与桶名都真的被跑过了。**上传与下载还没有。**
**iOS 完全没有测过** —— 这台机器上无法测。代码避开了已知在那里缺失的 API，并在可选 API 不存在时降级，
但那是推理，不是证据。Android 也没有在真机上跑过。

**桌面端的真机冒烟检查是过的**（`npm run verify:real`，通过 DevTools 协议驱动 Obsidian）：插件在真实宿主里加载、
四条命令全部注册、设置页可渲染（4 组 / 18 项），以及只有真实 WebView 才能定论的那一点 —— 实时预览的 `src`
拦截装上了且不破坏任何东西，并且不动站外地址。

它还回答了类型声明回答不了的问题：**本插件调用的那些宿主 API，在运行时到底存不存在。** 这在本项目里不是假设 ——
`adapter.getBasePath` 有声明，但在移动端会抛错。所以检查还确认了 `Vault.delete` 真的存在（删缓存文件的唯一落点）、
`FileManager.trashFile` 也在（仍被「上传后不留本地副本」使用，那会删掉你自己的文件），以及同一个问题的镜像：
设置页里**确实没有**那个被砍掉的「缓存删除方式」—— 宿主渲染出来后，既没有那个设置值、也没有对应的控件。

它**不覆盖**的是任何需要人在键盘前的事：真的粘贴和拖入一张图、链接是否落在你期待的位置、Obsidian 自己的粘贴
处理是否被完全抑制，以及编辑过程中实时预览的拦截表现如何。最后这条是这个代码库里最不常规的地方，也是图片
显示错源时第一个该怀疑的地方。

**与原生行为的已知差异 —— 拖放文件。** 原生 Obsidian 把链接插在**指针落点**。本插件插在**光标位置**，
因为公开类型里没有任何「指针坐标 → 编辑器位置」的映射（1.13.0 的类型定义里搜不到 `coords` / `posAt` 类 API，
而伸手去拿 CodeMirror 的视图对象意味着依赖未公开的东西）。拖放时若光标在别处，链接就落在那里。
这是**有意取舍**，不是疏忽。

**已知限制 —— 改了存储地址之后的老链接。** 判断「这张图是我们的」依赖当前设置加上本地副本索引。如果你改了或
清空了公开 URL 前缀，**而**副本又不在索引里（新设备），那些老链接会被当作站外图片：原样显示，
**除非你明确同意过缓存那个站点，否则永不下载**（那条路径默认关闭，也是本项目里唯一会去取别人字节的代码）。
关掉那个功能、或对你拒绝过的站点，它们仍然能在线显示；离线则不能。这个选择是**有意**的 —— 另一条路是去猜
别人的 URL，那意味着把本来不属于你的图拉进你的 vault。

## 支持的 Obsidian 版本

需要 Obsidian **1.13.0** 或更新 —— 桌面端与移动端。

这个下限由插件用到的最新 API 决定，而现在是**声明式设置 API**（`getSettingDefinitions()`，1.13.0 引入）。
采用它是有意的取舍：设置项可被 Obsidian 的全局设置搜索搜到；条件行用谓词表达，而不是整页重渲染；简单的行完全
不需要读写代码。代价是真实的，值得直说 —— 最近几个月没更新过 Obsidian 的用户装不了这个插件，而上一个下限
（1.11.4，由 `SecretStorage` 决定）能覆盖他们。

秘密访问密钥仍然走 `SecretStorage`/`SecretComponent`（1.11.4），那低于下限，所以不再是约束。但访问密钥 **ID**
刻意不走：它是标识符而不是秘密，而 Obsidian 的密钥存储只接受小写的 ID —— 访问密钥 ID 常规就带大写，
所以它本来也存不进去（见下）。

这个数字不是估的。`obsidian` 类型包被**精确**钉在 `1.13.0`，于是 `tsc --noEmit`（`npm run build` 的一部分）
成了版本闸门 —— 用了更晚的 API 就编译不过。这是**探针实测**而非假定：当下限还是 1.11.4 时，调用
`DataAdapter.appendBinary`（1.12.3 引入）会以 `Property 'appendBinary' does not exist on type 'DataAdapter'`
失败，而本插件自己的源码在那套类型下编译是干净的。

这条闸门只在「钉住」成立时有效，所以 `npm run check:api-floor` 会在这些情况下失败：依赖变成 `^` 范围、钉住的
类型与 `minAppVersion` 不一致、或装上的包与声明不再匹配。任何一条都会让闸门变绿却什么都证明不了 ——
而一条悄悄不再检查的检查，比没有检查更糟。

`minAppVersion` 是按版本发布的：若某个后续版本需要更新的 API，那个版本的下限就升高，而 `versions.json` 让旧版
Obsidian 留在最后一个兼容版本上。

## 安装

插件还没进社区目录（开发中）。手动安装：

1. 构建或下载 `main.js`、`manifest.json`、`styles.css`
2. 把它们复制到 `<vault>/.obsidian/plugins/attachment-cloud-cache/`
   ⚠️ 目录名必须与插件 id 完全一致 —— `attachment-cloud-cache`
3. 在 Obsidian → 设置 → 第三方插件 → 已安装插件 里启用它

## 配置

1. 打开 **设置 → Attachment Cloud Cache**
2. 填 **Endpoint**、**Bucket**、**Region** 与 **Public URL base**
3. 填**访问密钥 ID**（普通输入框 —— 它是标识符不是秘密，含大写是正常的），然后在它**下面那一格**填
   **秘密访问密钥**；后者会写进 Obsidian 的钥匙串，而不是插件的数据里
4. 点 **测试连接**

## 披露

- **网络使用**：本插件只把你选择上传的附件发到**你自己**配置的 S3 兼容端点。它不与任何其它服务通信，
  也不含任何遥测。
- **vault 之外的文件**：不访问。插件读写的所有内容都在你的 vault 内。
- **秘密访问密钥**存在 Obsidian 的密钥存储（操作系统钥匙串）里，绝不写进 `data.json`。**访问密钥 ID**
  存在 `data.json` 里 —— 它是标识符而不是秘密（它本身就是被签名请求的一部分，也会出现在服务端日志里），
  而 Obsidian 的密钥存储只接受小写 ID，访问密钥 ID 却常规就带大写。单独拿到 ID 什么都签不了；
  需要保护的是秘密。

## 开发

```bash
npm install
npm run dev          # watch 构建
npm run check        # 构建 + lint + manifest + api-floor + 变异一致性 + 护栏 + 测试
npm run test:unit    # 只跑测试
npm run mutate       # 变异验证：每条规则的断言是否真的有牙齿
```

测试跑在 Node 上、不用测试框架 —— 该用真实的地方就用真实 HTTP 服务与真实文件系统而不是 mock，而 Obsidian 宿主
由一个替身接替，它还能模拟移动端受限的文件系统访问（`scripts/lib/mock-obsidian.mjs`）。

### 这里的「变异验证断言有牙齿」是什么意思

有测试不等于有**会失败的**测试。`npm run mutate` 刻意把源码里的每条规则改坏，重新加载，并要求测试套件
**因那条规则自己的原因**变红 —— 而不只是「变红」。如果某条规则被改坏后没有任何测试注意到，这一轮就会失败并报出
那条规则。

这不是仪式。它已经多次回本：抓出过被前面某个检查挡在后面、永远到不了的断言；一个没有任何测试能触发的退避上限；
一条会把每个粘贴的文件都并成一个的去重规则；以及最有用的一次 —— 一个真实的双重编码 bug，已编码的路径又被编码
一次，结果是上传成功但链接打不开。

这类保证很容易被无意中弄丢，所以 `npm run check` 还会跑 `scripts/check-mutate-files.mjs`。它静态地核实：每个变异
脚本**恰好**调用一次 `runMutations`（第二次永远不会执行，因为第一次就退出了进程 —— 而输出看起来仍然成功）、
每个变异脚本都真的列在 `npm run mutate` 里、以及每个共享断言套件都同时被一个测试与一个变异脚本使用。
一条悄悄停止运行的检查比没有检查更糟，所以接线本身也被核实。

同样的原则产出了 `scripts/check-api-floor.mjs`，它守着 [支持的 Obsidian 版本](#支持的-obsidian-版本) 里那个
`minAppVersion` 声明。那个声明依赖类型包保持钉住，而这正是那种会悄悄失效的不变量 —— 所以它被断言，而不是被相信。

还有 `scripts/check-no-dev-doc-refs.mjs`：它让仓库里不出现对**开发笔记**的引用，那些笔记放在仓库之外
（历史里也没有）。这条护栏扫**每一个文件**，也就是真正会被发布出去的那一份。它存在的理由很实际：
下一条想引「设计依据」的注释会很自然地写出来 —— 而读者就会去找一个这里根本不存在的文件。
